# SEAM repository analysis — 2 November 2026

This is the historical audit. See [the remediation report](remediation-2026-11-02.md) for the subsequent fixes, UI redesign and validation results.

Review target: `7178830` on `main`, plus the existing local checkout. Environment: Windows, Node 24.18.0, npm 12.0.0. CI targets Ubuntu and Node 22; that environment was not reproduced here.

The build and package integration work, but three independently reproduced gaps affect policy enforcement or the meaning of `chain_verified`. Those should be resolved before relying on SEAM to enforce transaction rules or independently verify execution. Passing existing tests does not cover these cases.

Across all five workspace suites: **1,936 passed, 8 failed, 13 skipped (1,957 total)**. The observed failures trace to Windows line endings or module/path handling. This does not establish the result on Linux CI.

This was source review, local execution, adversarial API reproduction, dependency auditing, and browser smoke testing. It is not a formal security audit. Application source and existing local changes were left intact. No transaction was broadcast and no user wallet was connected. Offline signature testing used only the public `//Alice` development account, with no signature bytes retained in this report.

## Confirmed high-priority findings

### 1. [P1] An allowed policy result can authorize a different, disallowed plan

Locations: `packages/policy/src/policy.ts:163`, `packages/policy/src/approval.ts:189`, `packages/policy/src/approval.ts:621`.

`evaluatePolicy` registers result object identities in a global `WeakSet`. A result carries a policy digest, but its provenance is not bound to the plan, runtime facts, preflight, or manifest that were evaluated. `createApproval` accepts a result for the same policy and builds a new binding around the supplied plan. At submission, `isEvaluatedPolicyResult(pr)` causes the gate to skip re-evaluation, including when `policyEvaluation` inputs are supplied.

Reproduction executed against built packages:

1. Compile a transfer to Bob and evaluate a policy allowing Bob only. Retain that genuine allowed result object.
2. Compile a separate manifest transferring to an AccountId32 outside the allow-list. A fresh policy evaluation correctly blocks this plan.
3. Pass the old allowed result alongside the new plan to `createApproval`, with the new manifest, live facts, and `requirePlanVerified: true`.
4. Sign the new plan locally with the public development account. Submit the signed bytes to `checkBeforeSubmit` using the real `signedExtrinsicDecoder`, `requireTrustedDecoder: true`, `requireEvaluatedPolicyResult: true`, `live: true`, matching block/nonce, and the new manifest/facts.

Observed:

```json
{
  "freshBadAllowed": false,
  "oldGoodAllowed": true,
  "approvalCreated": true,
  "gateAllowed": true,
  "reasons": []
}
```

The signature and plan-byte checks do not prevent this: they prove the new transaction matches its manifest, while the policy decision still belongs to another transaction. This is an API trust-boundary failure; the reproduction does not demonstrate an unauthenticated remote attack on the console.

Recommended change: associate each evaluated result with an immutable digest of all evaluation inputs and result contents, and verify that association at approval and submission. Alternatively, always re-evaluate with the actual inputs at those boundaries. Merely freezing the result object does not prevent reuse for another plan. Add regression cases for result reuse across plans, preflights, facts, and in-place result edits.

### 2. [P1] One transaction can prove two identical sequential steps

Locations: `packages/sdk/src/verify-live.ts:193`, `packages/sdk/src/verify-live.ts:248`.

The live SDK verifier checks each receipt step separately. It does not enforce distinct extrinsic identities for sequential steps, or their execution order. The reader exposes an on-chain nonce, but this verifier does not use it.

Reproduction: compile a sequential manifest with two transfers of 10 units to the same recipient, using different action IDs. Build both receipt steps with the same transaction hash and finalized block. Supply a reader containing exactly one transaction, one matching transfer event, the correct signer and call, and nonce 1.

Observed:

```json
{
  "status": "chain_verified",
  "problems": [],
  "notes": [],
  "steps": [
    { "actionId": "pay1", "status": "chain_verified" },
    { "actionId": "pay2", "status": "chain_verified" }
  ]
}
```

The receipt claims two transfers although the reader proves only one. An unkeyed receipt digest cannot prevent this because the altered receipt can be rehashed.

Recommended change: require a unique `(blockHash, extrinsicIndex)`/transaction identity per sequential step and validate ordered execution, using block/index order and decoded nonces where available. Preserve the legitimate shared-transaction handling for atomic batches. Test repeated identical calls as well as reversed sequential receipts.

### 3. [P1] Live contract verification can trust caller-supplied state as chain evidence

Locations: `packages/sdk/src/verify-live.ts:318`, `packages/sdk/src/verify-live.ts:344`, `packages/sdk/src/receipt.ts:471`.

`verifyReceiptLive` forwards `opts.effects[actionId].stateReadback` into `verifyStep`. The latter grants `effect_proven` when `actual === expected`. The live verifier does not fetch that `actual` value from its reader, which has no generic contract-state read method. The special handling for `revive.map_account` does strip caller-provided mapping evidence and perform a reader call; legacy `contracts.call` lacks equivalent handling.

Reproduction: compile one legacy contract call. The reader returns the correct finalized transaction, signer and call, but only `System.ExtrinsicSuccess` and no contract event or state read. Supply:

```js
effects: {
  call: { stateReadback: { expected: "settled", actual: "settled" } }
}
```

The resulting receipt and `verifyReceiptLive` both report success; the live result is `chain_verified` with no problems or notes. Its reader never read contract state.

Recommended change: treat caller-provided state as an assertion, not an observation. Read the actual value through a trusted reader at a specified finalized block, or keep verification `unknown` when only a supplied state value is available. Keep expected event assertions distinct from observed event data.

## Confirmed functional and portability findings

### 4. [P2] Configured `abiRef` plans cannot pass strict approval

Locations: `packages/sdk/src/flow.ts` (`opts`, `compile`, `approve`, `execute`); `packages/policy/src/approval.ts:121`; `packages/policy/src/policy.ts:222`.

`Seam` accepts ABI dictionaries as compile defaults, and compilation resolves `abiRef` correctly. The policy/approval fresh-compile paths pass only `allowAtomicUnverified` to `verifyPlan`; they have no route for the ABI dictionary. Consequently the required recompilation cannot resolve the reference.

Reproduction used the bundled ERC20 ABI, configured as `{ abis: { erc20: abi } }`, and a named `transfer` call with `abiRef: "erc20"`. Compilation returned `status: "ok"`, and policy without strict recompilation allowed it. `Seam.approve` with `manifest` and `requirePlanVerified: true` returned:

```text
Can't approve: the plan's call bytes are not what the Manifest compiles to on the live runtime (COMPILE_FAILED).
```

Recommended change: carry the pinned ABI inputs through all recompilation stages, including execute-time gates, and bind their hashes. Do not work around this by disabling plan-byte verification.

### 5. [P2] JSON policies cannot express supported deploy rules

Location: `packages/policy/src/policyFile.ts:27`.

`Policy` supports `deploy`, and the engine evaluates it, but `parsePolicy` does not include `deploy` in its known fields or validate it. Parsing a policy with a deploy object returns `ok: false` and `unknown field "deploy"; check the spelling`. The CLI's policy-file path therefore cannot represent these rules.

Recommended change: validate the complete `DeployPolicy` schema in the parser and retain it in the parsed policy. Add parser-to-engine integration coverage for both deployment and account-mapping rules.

### 6. [P2] Windows checkout conversion changes runtime fingerprints

Location: `packages/compiler/src/runtime.ts:80`; the repository has no `.gitattributes` file, and this checkout has `core.autocrlf=true`.

The legacy pinned JSON type file is intentionally hashed as exact text. Git converted its 28 line endings to CRLF on this checkout. With the same metadata and logical type definitions:

| Input                                | Fingerprint digest                                                   |
| ------------------------------------ | -------------------------------------------------------------------- |
| Current CRLF checkout                | `0x00177575248026f000a33fd3f9232c4a0c7951aec03f72b72ae3207aad73a75b` |
| Same text normalized to LF in memory | `0xfa84b636f16022d59470133e37c4130e936421a85d272363fb394b1116eba896` |

The LF result matches the committed golden fingerprint. This accounts for four compiler golden-test failures and changes plan digests and runtime-lock compatibility across checkouts.

The fresh V3 fixture check has a related portability failure: generated text is LF, committed checkout text is CRLF; they compare equal after normalizing the latter in memory.

The standard formatting check reported 351 files. Repeating it with `--end-of-line auto` passed all matched files, establishing that this formatting failure is due to line endings rather than hundreds of independent style defects.

Recommended change: pin LF for hash-sensitive and generated text with repository attributes. Preserve the intended raw-byte hashing contract; do not simply replace existing golden hashes or silently change the fingerprint algorithm.

### 7. [P2] Maintenance and test scripts mishandle Windows paths

- `scripts/evidence-manifest.mjs:8` uses a file URL's `.pathname` as a filesystem path. `node scripts/evidence-manifest.mjs --check` fails trying to scan `D:\D:\seam-portaldot\evidence`. Use `fileURLToPath`.
- `scripts/sdk-api-doc.mjs:14` dynamically imports a Windows absolute path string. It fails with `ERR_UNSUPPORTED_ESM_URL_SCHEME` (`d:`). Use file URLs for imports. This is the one SDK test failure.
- `packages/chain/tests/v3-discovery.test.ts:187` passes a raw Windows path to Node's `--import`. Node fails before the discovery script runs, causing two chain-test failures. A direct invocation confirmed this loader error. The discovery script itself still refused the mainnet URL when invoked directly.
- The quickstart's edited-receipt setup creates `/tmp/seam-quickstart/edited.json` through native Node, while Git Bash converts that path differently for the subsequent CLI command. The expected integrity-failure exit 5 becomes a file-not-found exit 1.

Recommended change: use file URLs for module loading, filesystem paths for filesystem access, and a single explicitly resolved temporary directory across shell and Node commands. Exercise Windows and Linux in CI if both are supported.

### 8. [P2] Landing-page instructions lead to a hidden live-mode control

Locations: `packages/console/src/App.tsx:298`, `packages/console/src/App.tsx:532`.

The landing page tells users to open the testnet console, connect a wallet and press Check live. A fresh console opens in OFFLINE DEMO instead. LIVE V3 is inside the collapsed disclosure named Recorded demos. The visible offline screen asks for runtime discovery and shows a mainnet RPC URL, while also showing a local-node banner. The live wallet and chain-check controls are inaccessible until the user discovers that disclosure and changes modes.

This was observed in the production build, not inferred only from code. After choosing LIVE V3, the builder's read-only discovery worked and displayed `portaldot-v3`, spec 3002.

Recommended change: make the landing-page path open LIVE V3 directly, or expose a clearly named top-level mode choice with an explicit path for the offline demo. Align the initial screen with the landing instructions.

## Limits and next actions

The throwaway Linux-node E2E test was not completed: Ubuntu under WSL failed to start with `Wsl/Service/CreateInstance/CreateVm/0x800705b4`. The regular chain suite's live/local-node opt-in cases remained skipped. Browser discovery is not a substitute for a new signed/finalized run.

The ink! contract's offline Rust test attempt was blocked because the `ink` crate was absent from the local Cargo cache. Contract sources were inspected, but the Rust contract tests and Solidity deployment/behavior tests were not executed. No assertion of contract security follows from that source inspection.

Historical chain evidence was exercised by the existing replay/verifier suites; it was not all re-fetched from the public chain. No deployed production environment, authenticated wallet flow, or exhaustive device/accessibility matrix was tested.

Fix and regression-test findings 1–3 first. Then restore the strict ABI flow, policy-file parity and cross-platform checks, resolve development-tool advisories, and repeat the Linux E2E and actual wallet flow in an explicitly authorized disposable test environment.
